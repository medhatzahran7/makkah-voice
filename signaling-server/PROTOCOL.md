# بروتوكول رسائل خادم الإشارة — «شبكة الناس»

اتصال WebSocket واحد لكل **جهاز**؛ وقد يكون للبرج الواحد عدة أجهزة
متصلة في آن واحد (نفس الهوية على تليفونين بعد نقلها بـ QR) — الحضور
يبقى إدخالاً واحداً لكل `towerId`. رسائل JSON نصية فقط. كل الرسائل
كائنات JSON فيها حقل `type`. الحد الأقصى لحجم أي رسالة **1MB**، والحد
الأقصى للمعدل **60 رسالة/دقيقة لكل اتصال** — عند التجاوز يرد الخادم
`{type:"error", code:"rate_limited", ...}` وتُسقَط الرسالة.

## الانضمام والحضور

### العميل → الخادم: `join`

```json
{ "type": "join", "room": "cairo-1", "node": 3,
  "towerId": "tower-3-a1b2c3",
  "name": "برج 3", "uname": "مدحت", "ucolor": "#d4a853", "uicon": "🏬",
  "super": false, "device": "device-id", "tab": "tab-id" }
```

- `room` (إلزامي): نص غير فارغ حتى 64 حرفاً.
- `node` (اختياري): رقم البرج 1–8. إن غاب يختار الخادم أقل رقم متاح.
  إن كان الرقم مشغولاً ببرج آخر يرد خطأ `node_taken`؛ وإن امتلأت الغرفة
  (8 أبراج) يرد `room_full`.
- `towerId` (اختياري): هوية البرج. إن غابت يولّدها الخادم
  (`tower-<node>-<6 hex>`).
- `device` (اختياري لكنه مهم): معرّف الجهاز المتصل. الهوية الكاملة
  للاتصال هي الزوج (`towerId` + `device`):
  - إن أُعيد الانضمام **بنفس الزوج** يستبدل الخادم الاتصال القديم
    ويغلقه بالكود `4001` (هذا هو مسار إعادة الاتصال التلقائي من العميل).
  - إن انضم **جهاز مختلف بنفس `towerId`** (نفس الهوية على تليفون آخر)
    يتعايش الجهازان: يرث الجهاز الجديد رقم برج البرج نفسه (`node`)،
    ولا يُحسب برجاً إضافياً في حدّ الـ 8 أبراج، ولا يُبث `peer-joined`
    لانضمامه (البرج حاضر أصلاً). عميل قديم لا يرسل `device` يُعامل
    كجهاز واحد بمعرّف فارغ، فيبقى سلوكه القديم: إعادة الانضمام بنفس
    `towerId` تستبدل الاتصال.
- باقي الحقول معلومات حضور اختيارية (نفس حقول حمولة الحضور في النموذج
  الويب v3.3: `name/uname/ucolor/uicon/super/call/relayLoad/device/tab`).

### الخادم → العميل: `joined`

```json
{ "type": "joined", "room": "cairo-1", "towerId": "tower-3-a1b2c3",
  "node": 3, "peers": [ { "towerId": "...", "node": 1, "name": "برج 1", ... } ] }
```

`peers` قائمة الأبراج الحاضرة في الغرفة لحظة الانضمام (بدون نفسك) —
إدخال واحد لكل `towerId` مهما تعددت أجهزته.

### الخادم → الغرفة: `peer-joined` / `peer-left`

```json
{ "type": "peer-joined", "room": "cairo-1",
  "peer": { "towerId": "...", "node": 2, "name": "برج 2", "call": "idle", ... } }

{ "type": "peer-left", "room": "cairo-1", "towerId": "...", "node": 2,
  "reason": "disconnect" | "leave" | "timeout" }
```

يُبث `peer-joined` عند انضمام **أول جهاز** من البرج فقط، ويُبث
`peer-left` عند مغادرة **آخر جهاز** منه فقط؛ مغادرة جهاز وبقاء جهاز
آخر من نفس البرج لا تغيّر الحضور. قائمة الحضور الكاملة (`presence`)
فيها إدخال واحد لكل `towerId` (يمثله أول جهاز انضم).

### العميل → الخادم: `heartbeat` (كل 5 ثوانٍ، كما في v3.3)

```json
{ "type": "heartbeat" }
```

الرد: `{ "type": "pong", "ts": 1732... }`.
إن صمت برج **15 ثانية** يزيله الخادم من الحضور ويبث `peer-left`
بسبب `timeout`. انقطاع الاتصال نفسه (إغلاق الـ socket) يزيل البرج فوراً
(last-will) ويبث `peer-left` بسبب `disconnect` — بلا انتظار المهلة.

### العميل → الخادم: `presence` (تحديث معلومات الحضور)

```json
{ "type": "presence", "call": "busy", "relayLoad": 2 }
```

أي حقل من حقول الحضور؛ الخادم يحدّثها ويبث القائمة الكاملة:

```json
{ "type": "presence", "room": "cairo-1", "peers": [ {...}, {...} ] }
```

### العميل → الخادم: `leave`

```json
{ "type": "leave" }
```

يخرج البرج من الغرفة (ويبث `peer-left` بسبب `leave`) ويبقى الاتصال
مفتوحاً لانضمام جديد. الرد: `{ "type": "left" }`.

## إشارات WebRTC

### العميل → الخادم: `signal`

```json
{ "type": "signal", "to": "tower-2-xxxx", "signalType": "call-offer",
  "sdp": { "type": "offer", "sdp": "v=0\r\n..." }, "mode": "av" }
```

`signalType` أي نوع من أنواع v3.3: `call-offer` / `call-answer` / `ice` /
`data-offer` / `data-answer` / `data-ice` / `group-invite` / `group-leave`
وغيرها. الحقول `sdp` و`candidate` و`mode` و`groupId` و`renegotiate`
تُمرَّر كما هي — الخادم **لا يقرأ SDP ولا ICE أبداً**.

### الخادم → المستلم: `signal`

```json
{ "type": "signal", "from": "tower-1-xxxx", "to": "tower-2-xxxx",
  "signalType": "call-offer", "sdp": {...}, "mode": "av" }
```

الخادم يضيف `from` فقط. إن كان المستلم غائباً عن الغرفة يرد للمرسل
خطأ `peer_not_found`. إن كان للبرج المستلم عدة أجهزة متصلة تُسلَّم
الإشارة إلى أول جهاز انضم (الأقدم).

## الرسائل المشفرة (sealed sender)

### العميل → الخادم: `message`

```json
{ "type": "message", "to": "tower-2-xxxx",
  "envelope": "<base64: ظرف مشفر opaque>" }
```

### الخادم → المستلم: `message`

```json
{ "type": "message", "envelope": "<base64: الظرف كما وصل بالضبط>" }
```

**الخادم يمرّر فقط:**

- لا يضيف أي هوية مرسل (`from`) — المستلم وحده يفتح الظرف ويعرف المرسل.
- لا يسجّل محتوى الرسالة ولا هوية المرسل معها ولا يخزّنها.
- الظرف يصل **بايتاً ببايت** كما أُرسل؛ أي حقل `from` يرسله العميل
  يُتجاهل ويُسقَط.

إن كان المستلم غائباً يرد للمرسل خطأ `peer_not_found` (دون أي معلومة
عن المحتوى). إن كان للبرج المستلم عدة أجهزة متصلة يُسلَّم الظرف إلى
أول جهاز انضم (الأقدم).

## مزامنة السجل بين أجهزة الهوية نفسها

بعد نقل الهوية بـ QR يملك الجهازان نفس البذرة ونفس `towerId`. لمزامنة
سجل الدردشات والمكالمات من جهاز إلى آخر يرسل العميل رسائل من أنواع
`sync-request` / `sync-offer` / `sync-chunk` **موجَّهة إلى `towerId`
الخاص به** (`to` = هويته هو)؛ فيوزّعها الخادم على **الأجهزة الأخرى من
نفس `towerId` فقط** — لا يعيدها للمرسل ولا يرسلها لأي برج آخر.

```json
{ "type": "sync-request", "to": "tower-3-a1b2c3",
  "syncId": "9f2c…", "fromDevice": "dev-abc" }

{ "type": "sync-offer", "to": "tower-3-a1b2c3",
  "syncId": "9f2c…", "fromDevice": "dev-xyz",
  "messageCount": 120, "callCount": 15, "chunks": 3 }

{ "type": "sync-chunk", "to": "tower-3-a1b2c3",
  "syncId": "9f2c…", "index": 0, "total": 3,
  "nonce": "<base64: 12 بايت>", "data": "<base64: الدفعة المشفرة>" }
```

- `syncId`: معرّف عشوائي لجلسة المزامنة الواحدة؛ يردّ به الطرف الآخر
  في العرض والدفعات، ويتجاهل العميل أي رسالة مزامنة لا تحمل `syncId`
  جلسته النشطة.
- `fromDevice`: معرّف الجهاز المرسل (لمعرفة الطرف الآخر؛ الخادم لا
  يضيف `from` لهذه الرسائل).
- `sync-offer`: عدد الرسائل/المكالمات المتاحة وعدد الدفعات؛ إن كان
  السجل فارغاً يكون `chunks: 0`.
- `sync-chunk`: دفعة مشفرة AES-GCM بمفتاح مشتق من بذرة الهوية
  (HKDF، `info = "wasla/history-sync-v1"`) — الدفعة JSON حتى **200KB**
  قبل التشفير، و`nonce` عشوائي 12 بايت لكل دفعة. حقل `data` معتم
  تماماً بالنسبة للخادم: لا يقرؤه ولا يسجّله ولا يخزّنه، ويمرّره كما هو.
- الأخطاء: إن لم يكن هناك جهاز آخر من نفس الهوية متصلاً يرد الخادم
  للمرسل `{type:"error", code:"sync_no_peer", ...}`؛ وإن وُجّهت رسالة
  مزامنة إلى `towerId` غير هوية المرسل يرد
  `{type:"error", code:"invalid_sync", ...}`.
- رسائل المزامنة تُحسب ضمن حدّ المعدل (60 رسالة/دقيقة لكل اتصال)
  وحدّ الحجم (1MB) مثل غيرها.
- المزامنة لحظية: تتطلب أن يكون الجهازان متصلين بالخادم في نفس اللحظة
  وبنفس الهوية؛ لا يوجد تخزين أو طابور على الخادم، فجهاز غير متصل لحظة
  الطلب لا يصله شيء.

## حزم المفاتيح العامة (بروتوكول Signal — المرحلة 2)

حزمة المفاتيح **عامة فقط** — أي حزمة تحتوي حقلاً باسم يوحي بمفتاح خاص
(`privateKey`, `secret`, …) تُرفض. التخزين في الذاكرة مع حفظ دوري في
`data/keybundles.json`.

### العميل → الخادم: `key-bundle` (تخزين)

```json
{ "type": "key-bundle", "action": "put",
  "bundle": {
    "identityKey": "<base64: مفتاح X25519 العام>",
    "signedPreKey": { "id": 1, "key": "<base64>", "signature": "<base64>" },
    "oneTimePreKeys": [ { "id": 101, "key": "<base64>" } ]
  } }
```

تُخزَّن تحت هوية البرج المنضم. الرد:
`{ "type": "key-bundle", "action": "put", "towerId": "...", "ok": true }`.

### العميل → الخادم: `key-bundle` (جلب)

```json
{ "type": "key-bundle", "action": "get", "towerId": "tower-2-xxxx" }
```

الرد:

```json
{ "type": "key-bundle", "action": "get", "towerId": "tower-2-xxxx",
  "bundle": { "identityKey": "...", "signedPreKey": {...},
              "oneTimePreKeys": [ { "id": 101, "key": "..." } ] } }
```

سلوك X3DH: كل جلب يسلّم **مفتاحاً واحداً لمرة واحدة بالضبط** ويحذفه من
المخزن فلا يُسلَّم مرتين أبداً. إن نفدت المفاتيح لمرة واحدة يرجع
`oneTimePreKeys: []` (وتبقى الهوية والمفتاح الموقّع صالحين للجلب).
برج بلا حزمة مخزنة يرد خطأ `key_bundle_not_found`.

## الأخطاء

```json
{ "type": "error", "code": "node_taken", "message": "Tower 3 is already taken in this room." }
```

| الكود | المعنى |
|---|---|
| `invalid_json` | الرسالة ليست JSON صالحاً |
| `invalid_message` | ليست كائن JSON أو حقول ناقصة |
| `unknown_type` | نوع رسالة غير معروف |
| `invalid_room` | اسم غرفة غير صالح |
| `invalid_node` | رقم برج خارج 1–8 |
| `node_taken` | رقم البرج مشغول في الغرفة |
| `room_full` | الغرفة ممتلئة (8 أبراج) |
| `already_joined` | منضم بالفعل — أرسل `leave` أولاً |
| `not_joined` | يلزم الانضمام لغرفة أولاً |
| `invalid_signal` | إشارة ناقصة (`to`/`signalType`) أو للذات |
| `invalid_message` | رسالة ناقصة أو الظرف فارغ |
| `peer_not_found` | البرج المستلم ليس في الغرفة |
| `invalid_key_bundle` | حزمة مفاتيح بشكل خاطئ أو فيها مفتاح خاص |
| `key_bundle_not_found` | لا حزمة مخزنة لهذا البرج |
| `invalid_sync` | رسالة مزامنة موجَّهة إلى غير هوية المرسل |
| `sync_no_peer` | لا جهاز آخر من نفس الهوية متصل الآن |
| `rate_limited` | تجاوز 60 رسالة/دقيقة — أبطئ |
